# 团队项目知识门户

## 核心原则

**先读仓库里已经写好的东西，不要一上来就翻代码。**

团队已经把知识写在仓库里了——`CLAUDE.md`、`AGENTS.md`、`.claude/skills/`。
这些是有人花时间整理过的，优先级高于你现场读代码推断出来的结论。

**每一句结论都要能指回来源文件。** 用户要的是"大概了解 + 知道去哪深入"，
不是一份听起来专业但无从查证的综述。

## 读取优先级

按信息密度排序，**读到够用就停**，不必读全：

| 顺序 | 位置 | 回答什么问题 |
|---|---|---|
| 1 | `.claude/skills/*/SKILL.md` | **"怎么做"**——团队沉淀的具体操作流程 |
| 2 | `CLAUDE.md` / `AGENTS.md` | **"是什么"**——项目定位、架构、目录职责、约定 |
| 3 | `README.md` | 同上，但质量参差，**先看大小** |
| 4 | 子目录的 md（`docs/`、各组件的 `README.md`） | 深入某个具体主题时 |

### 第 3 层的过滤

`README.md` 的**地板极低**——实测见过 24 字节的（`# osi-task-manager` + `TODO`）。

- **< 1KB**：基本无信息量，快速扫一眼即可，不要当作有效来源
- **1KB ~ 5KB**：通常只讲了"是什么"，读
- **> 5KB**：可能有实质内容，认真读

### 两层都读，不要只读一个

`CLAUDE.md` 和 `README.md` **可能互相矛盾**——实测遇到过：
`CLAUDE.md` 写环境变量是 `SMTP_HOST`，`README.md` 写 `smtp_host`，
而代码读的是后者。**优先级更高 ≠ 更准确。**

两份都存在时都读，发现冲突就**以代码为准**并指出矛盾。

## 执行流程

### 第 1 步：定位门户文档

```bash
ls -la CLAUDE.md AGENTS.md README.md 2>/dev/null
ls .claude/skills/ 2>/dev/null
```

**注意命名不统一**：实测团队里有的用 `CLAUDE.md`，有的只用 `AGENTS.md`，
有的两个都有（内容可能不同步）。所以是**扫列表**，不是找单一文件名。

### 第 2 步：按优先级读

第 1 层（skills）优先——如果用户问的是"怎么做某件事"，
skill 里通常有现成的、团队验证过的步骤，**直接复用，不要自己重新推导**。

**读取路径注意**：harness 通常只会自动加载根目录的 `CLAUDE.md` / `AGENTS.md`，
`.claude/skills/` 下的 SKILL.md 需要你按上表主动去读——它们不会被自动塞进上下文。
**不要因为"没看到 skill 内容"就以为仓库没有 skill。**

### 第 3 步：回答并给出处

**每条结论后面标来源**，格式 `文件:行号`。用户要能自己跳过去深入。

### 第 4 步：如实说明覆盖边界

**这是这个 skill 最重要的一步。**

读完文档后，明确告诉用户：哪些问题文档答得了，哪些答不了。
不要用读代码推断出来的内容去填补文档的空白却不说——那会让用户
以为"文档里写了"，从而失去了自己去看的机会。

## 当文档不存在或太薄时

**不要说"没找到文档"就结束。** 按下面处理：

1. **先说清楚现状**："这个仓库没有 CLAUDE.md / AGENTS.md，README 只有 34 字节"
2. **退到文件系统事实**：顶层目录结构、主要文件类型分布、`.claude/` 有无配置
   ——这些是客观事实，可以从 `ls` / `find` 直接得出，不需要推断
3. **明确标注这是"目录结构"而非"项目知识"**，不要混为一谈
4. **如果用户问的是"怎么做"**，而文档和 skill 都没有——
   **如实说答不了**，并建议去问谁（`CLAUDE.md` 里通常有联系人/邮箱）

## 一个重要提醒

如果读完发现文档**内容翔实但和实际对不上**（比如让用户跑的命令不存在，
或环境变量名与代码不符），那是文档可信度问题，**不要自己绕过它继续回答**。

处理方式：

1. **当场指出矛盾**，并给出代码里的实际情况（`文件:行号`）
2. 提示用户可以跑 `doc-reconcile` 做一次系统对账，
   把悬空引用、覆盖缺口、失效 skill 引用一次性查出来

两者分工：`portal` 是**语义对账**（读文档 + 读代码，发现"说得对不对"），
`doc-reconcile` 是**机械对账**（只比对路径，发现"对不对得上"）。
覆盖的失效类型几乎不重叠，**发现一处矛盾时值得把另一样也跑一遍**。

## 不要做的事

- ❌ 不要为了"答得全"而把读代码猜出来的内容混进文档结论里
- ❌ 不要在文档没覆盖时假装覆盖了——**静默的空白比明确的空白更危险**
- ❌ 不要复述整篇 CLAUDE.md，用户要的是针对他问题的答案
- ❌ 不要因为文档写得自信就默认它是对的（实测过：写得越自信越可能是过期的）

## 范围说明

本 skill 负责**项目知识**：这个项目是什么、怎么组织、约定是什么、怎么参与。

**不负责部署运维类问题**（测试环境、上线发布）——那部分由独立模块承载，
不在本插件的知识补全范围内。被问到时要如实说明，不要硬答。
