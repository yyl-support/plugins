# 门户文档对账

## 为什么需要这个

团队仓库的门户文档（`CLAUDE.md` / `AGENTS.md` / `README.md`）是新人上手的第一入口。
但它们有两个**静默**失效模式——文档不会告诉你它有问题：

1. **悬空引用**：文档里写着"运行 `python3 foo.py`"，而 `foo.py` 早已删除。
   新人照做的第一条命令就报错，且不知道是环境问题还是文档问题。
2. **覆盖缺口**：仓库里有一整套子系统，文档一个字没提。
   新人会认为"文档里没有 = 不存在"。

这两类问题**机械对账就能发现**，不需要读代码、不需要建图。
本 skill 就是做这件事。

## 怎么跑

传入仓库的**本地路径**（脚本需要能读文件树）：

```bash
python3 <本 skill 所在目录>/scripts/reconcile.py <repo_dir>
```

**脚本位置**：`reconcile.py` 就在本 SKILL.md 同级的 `scripts/` 目录下。
不同 harness 定位方式不同：

- Claude Code：`"${CLAUDE_PLUGIN_ROOT}/skills/doc-reconcile/scripts/reconcile.py"`
- 其他（opencode 等）：按本文档自身的路径推导，或先 `find` 定位一次

如果用户只给了仓库名、本地没有克隆，先确认路径；需要联网拉取时用 `gh`
或 `git clone --depth=1`。

**脚本零依赖**（只用标准库），单仓耗时 < 1 秒（3,000 文件量级）。

### 支持的 Python 版本

Python 3.8+。未使用任何 3.9+ 专有语法。
（`dict` 合并运算符 `|` 在 3.9+ 才可用，脚本中未使用；如需改动请留意。）

## 输出怎么解读

脚本会给三类结果，**信噪比不同，必须分级处理后再报给用户**：

### A. 悬空引用 —— 优先级最高

"高置信"档是明确声称的文件，基本都可直接采信，**这是最该报给用户的一类**：
新人第一天就会踩到。

"待确认"档是目录引用，**需要人工判断**：

| 例子 | 判断 |
|---|---|
| `data/`、`community/` | 运行时生成的临时目录，**不是问题** |
| `hulk_robot_test/kernel_email_notification/` | 文档称其为"参考实现"，是真实存在的静态内容 → **真悬空** |

判据：文档描述它是**运行时产物**还是**仓库内容**。

**注意**：指向**其他仓库**的路径（如 `ascend-ci-project/CLAUDE.md`）会误报为悬空，
因为本地没有那个仓。这类直接排除。

### B. 覆盖缺口 —— 需要筛选

不是所有未提及的条目都值得报。**输出的排序已经按体积降序**，
越靠前越可能是主体内容。按用户价值筛：

| 类型 | 是否报 |
|---|---|
| 顶层源码目录 / 大文件（`tests/`、`common.py`、`scripts/`） | ✅ 报——文档漏了主体内容 |
| 真实部署入口（`Dockerfile`、`jenkins_job.sh`） | ✅ 报——新人最常问 |
| 配置文件（`.yamllint`、`.coveragerc`、`.gitignore`） | ❌ 不报——本就不需要文档 |
| 过程性文档（`PROGRESS_REPORT.md`、`*-record.md`） | ⚠️ 可提一句，不算缺陷 |
| 工具生成的目录（`.serena/`、`.idea/`） | ❌ 不报 |

**注意 `.github/` 与 `.claude/` 已被自动排除**：前者是 CI 配置，
后者由 C/D 两类单独覆盖，都不算"文档该讲的仓库内容"。

### C. Skill 引用 —— 如果有，优先级等同 A

`✗` 是文档声称但仓库中不存在的 skill，`○` 是存在但文档未收录的。
**这类问题最讽刺**：文档会专门写"选择指南"教用户在两个不存在的 skill 之间做选择。

**该档有已知漏报**：只能识别"带连字符的 `/skill-name`"或"行附近有
skill/触发/命令等语境词"的写法。若文档用裸词（如"用 arc-deploy 生成配置"，
无反引号无斜杠）提及 skill，检出不了。发现可疑时人工再扫一眼。

### D. Skill 文档对账 —— 优先级等同 A

对仓库内每个 `.claude/skills/*/SKILL.md` 跑同一套悬空引用检查。

**为什么重要**：根目录门户文档只是"门牌"，团队真正花心思写的知识在这层。
这些 skill 正文里会写"用 `templates/xxx.yaml` 这个模板"，
模板被挪走后 skill 就开始指向空气，且没有任何提示。

这一档噪声已压得较低，报出来的基本可直接采信。剩余 `?` 档（目录引用）
需人工判断，多为运行时路径。

**注意 D 类只查悬空引用，不查覆盖缺口**——skill 的"覆盖缺口"没有客观基准
（一个 skill 该覆盖什么，取决于它想教什么），强行检测只会产生噪声。

## 报告方式

**按"新人踩坑概率"排序，不要按发现顺序罗列。** 建议结构：

```markdown
## 结论
<这个仓库的文档可信 / 不可信，一句话）

## 会直接坑到新人的（N 处）
- 第 28 行 `members_change_attention.py` —— 文档写在 Build & Run 章节，文件不存在

## 文档没覆盖的（N 处）
- `tests/`（5 文件 / 79KB）—— 全部测试未提及

## 可忽略的（N 处）
- `.yamllint`、`.coveragerc` 等配置文件
```

**不要只丢脚本原始输出**——脚本有噪声，分级和筛选才是这个 skill 的价值。

## 边界（诚实说明）

对账解决的是**"对不对得上"**，解决不了**"说得对不对"**：

- 文件存在但内容已过时 → 检不出
- 文档提了 `tests/` 但没说怎么跑测试 → 检不出（语义问题）
- 描述与实现行为不符 → 检不出
- **文档与环境变量/配置项不符 → 检不出**
  （实测遇到：`CLAUDE.md` 写 `SMTP_HOST`，代码读 `smtp_host`，全小写。
  邮件静默发不出去。这类问题只有同时读文档和代码才暴露，
  建议配合 `portal` skill 交叉验证。）

检出 0 个问题**不等于文档没问题**，只说明它自洽。
报告时如实说明这一点，不要给出过度保证。

**误报处理**：脚本对下列情况已有内置排除，无需再报——
跨仓库引用、容器内绝对路径（`/work/...`）、占位符（`{cluster}/...`）、
glob 模式、散文省略号（`.../pvc.yaml`）、k8s 注解键、IP/CIDR。

## 当前范围

- ✅ 仓库根目录**全部**门户文档——`CLAUDE.md`、`AGENTS.md`、`README.md` 有几份查几份
- ✅ `.claude/skills/*/SKILL.md`
- ❌ `docs/` 及其他子目录下的 md（同样会过期，尚未覆盖）
- ❌ 跨仓库引用（如 `other-repo/docs :: path`）——本地无从校验，已自动跳过

**为什么都查**：实测中 `pr-issue-report` 只查 `CLAUDE.md` 时报出 7 个覆盖缺口，
补上 `README.md` 后降到 3 个——`common.py`、`Dockerfile` 等其实 README 都写了。
**只读一份会同时造成漏报和误报。**

报告时按文档分段，冲突要单独指出：两份文档可能都引用了同一个不存在的文件
（`pr-issue-report` 的 `hulk_robot_test/` 就是 CLAUDE.md 和 README.md 都提了），
但也可能互相矛盾——那是最值得报的一类。
